# Independent adversarial implementation review

Reviewed commit: **`f0b3ea506d0a18b044f1b4908c50ed18a267add5`**, branch `quotis-2.0`, against **`f80bc4062ca589a79ef5dbb7a4f45b434b3aa3f7`**. Review date: 2026-11-15. Baseline reference: `docs/reviews/0001-baseline-codex.md`. All implementation line numbers refer to the reviewed commit, before this report's commit.

The extraction into a shared core, registry-driven interfaces, explicit quota provenance, strict minimum response checks, text-only DOM construction, and removal of screen capture are substantial repairs. The implementation nevertheless retains data-integrity and availability defects: snapshot publication is unordered, settings have a second unsynchronized writer, local errors can disappear, replacement logs retain old usage, and future observations can defeat newer real quota readings. Passing tests do not establish the desktop coordination guarantees claimed by the comments.

There are **7 FIXED, 10 PARTIAL, and 1 NOT FIXED** baseline findings under the definitions below. The new-findings table records **16 findings: 13 MEDIUM and 3 LOW**. No CRITICAL or HIGH exploit was established. MEDIUM denotes a demonstrated or explicitly source-derived integrity/availability problem with bounded impact; LOW denotes narrower presentation, validation, or assurance debt. Conditional failure scenarios are identified rather than described as observed production crashes.

**Executed** means an authorized build/test or a synthetic probe invoking the actual public core API/CLI/formatting functions. **Interleaving** means an explicit possible ordering of the implementation's operations; it does not claim a running desktop stress test. **Source proof** means a direct branch or absent boundary, with the trigger stated. FIXED closes the original baseline mechanism; PARTIAL means important repairs exist but a material part or variant remains; NOT FIXED means the original finding remains substantially intact. New IDs include newly identified mechanisms in areas also covered by a baseline finding, with cross-references to avoid counting them as independent repair successes.

No desktop app was launched and no screen, mouse, or keyboard automation was used. No live provider request was made. Network unit tests used loopback fixture servers and synthetic tokens. Package/dependency installation was not a provider test. No real credential file or value was inspected or printed.

## Architecture and boundary assessment

The provider registry and shared normalized model are useful extension points. However, `Engine` describes itself as doing no I/O while both construction/settings application and statuses synchronously call adapters' detect methods (`engine.rs:1`, `:127`, `:332`). The desktop consequently cannot treat an Engine operation as safe under its mutex. Separate scheduling/state transitions from discovery and make all adapter calls explicit off-lock work, including watcher configuration and environment/key detection.

`Outcome = Option<Result<Collected, ProviderError>>` loses distinctions needed for truthfulness. None can mean unsupported source, source disappeared, or no work; empty success may mean valid unlimited data, no usable log records, or a partial scan. Merge-by-ID then retains old local metrics, while API metrics are deleted wholesale before a merge. The model should say which source/account a complete observation replaces, whether collection coverage is complete, and whether absence invalidates earlier data. Configuration generation alone cannot supply request ordering or account identity. Timestamp comparison needs validated observations plus sequence IDs, not a single untrusted wall clock.

Publication and persistence are separate transactions from Engine state. Unique temporary filenames and rename solve torn-file visibility, but not ordering, loss of disabled-provider preferences, retry after failed writes, or crash durability. A single owner for revisioned app state, settings, and snapshot publication would make these invariants reviewable without enlarging the mutex to include disk writes or native-window calls. The current global SAVING lock only covers one writer.

Network credential routing is materially better: fixed HTTPS URLs in each adapter (`claude.rs:105`, `codex.rs:107`, `copilot.rs:78`, `cursor.rs:107`, `apikey.rs:86`, `:140`) and `max_redirects(0)` (`net.rs:12`) prevent ordinary redirected cross-host credential forwarding. Copilot preserves public-host provenance and refuses enterprise-host entries (`copilot.rs:31`). API keys are opt-in, read from their dedicated environment variables, and not serialized (`apikey.rs:11`, `:17`, `:32`, `:100`). Disabled providers short-circuit detection in Engine. Credentials are absent from the Snapshot schema and current normal serializers; generic network error strings omit request contents. No direct credential-to-Snapshot/CLI/log path was established. The panic hook is still process-global and catch_unwind does not redact an arbitrary future adapter's panic text; this is a boundary to enforce when extending adapters, not evidence of a present secret leak.

The CLI cache mode is network-free and its documented missing/stale/incompatible/malformed/unknown-provider exit codes are exercised successfully. `--live --offline` uses local collectors only and does not write the snapshot. Exit 0 currently means the requested snapshot was obtained within the cache-age contract, even if individual providers failed; consumers must inspect provider errors and per-metric freshness. It is not a universal "all quotas current" signal. A live diagnose collects all enabled providers before checking its requested ID (`quotis-cli/src/main.rs:286`, `:315`), and flags such as --provider/--format are accepted on commands that do not use them; these are contract ambiguities worth tightening, not additional proved security exploits. On macOS, live Claude access can invoke `/usr/bin/security`, so the CLI source comment claiming it never runs another program is inaccurate (`quotis-cli/src/main.rs:5`).
